# YipYip Project Context

Last updated: 26 September 2026

## Product

YipYip is an autonomous lead engine. A workspace configures one editable Lead Strategy, approves reputable sources once, and then receives automatically discovered, assessed, researched, and qualified Leads. Humans review finished Leads and genuine exceptions—not routine assessment steps. `PRD.md` version 2.0 is the product source of truth.

## Implemented

Theme and locale are first-party cookie preferences applied in the root server layout; source-authored evidence remains in its original language. Basket state is reconciled against the current Opportunity set so removed, reset, or quarantined items cannot leave a stale badge count.
- Authenticated Source Network at `/sources?workspace=<uuid>` with explicit workspace selection, editable/versioned Lead Strategy, automation summary, source approval inbox, approved monitors, workflow history, and exceptions.
- Browser-local `/sources?demo=empty` simulation: the Source Network now mirrors the live persistent operations screen and reuses its complete Lead Strategy fields, summary, runner, approval inbox, approved monitors, activity, and exceptions. Save strategy → automatic Source Scout → individual approval → automatic monitor/normalize/resolve/assess/gap/research/reassess/route → two qualified Leads plus one Needs-attention exception. Repeat monitoring demonstrates exact-match deduplication. It never calls Supabase or OpenAI.
- `20260924111240_autonomous_lead_workflow.sql`: Lead Strategy automation fields, legacy query-pack archival, source reputation separate from health, candidates, weekday jobs, workflow/stage leases, exceptions, role-scoped RPCs, same-workspace qualification references, and service-only dispatch/worker functions.
- `20260924124107_live_operator_controls.sql`: authenticated workspace onboarding, current-strategy source carry-forward, superseded-work cancellation, one-active-workflow constraints, atomic retry/exception-research RPCs, bounded research pass identity, workspace-scoped service claims, and operator source-monitor queueing.
- `20260924154613_correct_empty_source_scout_state.sql`: repairs historical zero-proposal Source Scout workflows that were incorrectly left at `waiting_approval`; future zero-reviewable runs finish successfully with an explicit empty result.
- Timezone-aware weekday scheduling at local 07:00, including Amsterdam DST; frequent Cron is expected to call a protected Next.js endpoint, which dispatches due work and processes one stage.
- Specialized bounded OpenAI agents for Source Scout, source monitoring, First/Final Assessment, Gap Analysis, and focused Research. Application code validates evidence, calculates scores, handles idempotency/retries, and routes outcomes.
- Search agents require an observed hosted-search call and accept evidence URLs only from raw web-search sources or URL-citation annotations. Custom API roots receive a narrow modern-to-preview search compatibility fallback.
- Search-agent Responses explicitly include `web_search_call.action.sources`, so deterministic citation validation receives the provider's consulted URLs instead of trusting URLs emitted by the model. Source Scout records generated, evidence-rejected, suppressed, and reviewable proposal counts.
- Source Scout now separates its strict structural provider schema from the bounded application contract. Safe text/item excesses are normalized, every proposal is validated independently, invalid siblings cannot erase valid proposals, and generated-but-wholly-invalid output is not misreported as a zero-result run. Only sanitized contract paths/codes are persisted.
- Source Scout is coverage-aware under `source-coverage-v1`: each run inventories approved/pending/rejected source domains, counts configured signal-area coverage, sends the bounded gap context to the agent, and prioritizes uncovered/lowest-covered areas. Deterministic application selection rejects active-domain repeats, same-run duplicates, off-strategy gaps, and concentration above two proposals per gap or normalized family. Up to five proposals and six hosted-search calls are allowed; coverage context, novelty reasons, and rejection counts remain in workflow/stage JSON snapshots without a schema migration.
- Agent-facing URL fields use strict-output-compatible bounded strings; deterministic application validation still requires canonical HTTPS URLs, citation allow-list membership, and source-host agreement before persistence.
- Research Agent `value` output is a bounded nullable string rather than an unconstrained JSON value, ensuring every nullable `anyOf` branch has an explicit OpenAI strict-schema type. Historical JSON-valued findings are normalized to bounded text before final reassessment.
- Deep research is potential-aware and bundle-scoped: commercial, buyer-access, capability, timing, and other questions run separately (maximum three questions per pass), with at most two attempts per question and eight passes under the existing workflow cost limit. A first semantic unknown/not-found answer receives one diversified continuation. Strongly inferred claims require two cited sources; consulted URLs remain separate attempt telemetry.
- Every focused Research response now sends `max_tool_calls = 3` to the Responses API and records that cap. Prompts prioritize the highest-value queries and accept unknown rather than expanding past the pass limit. Hosted-call telemetry is deduplicated by provider call ID because the Agents SDK retains normalized, nested provider, and raw representations of the same call.
- Operational estimates use a versioned Standard-price registry for supported OpenAI models, cached-input tokens reported by the provider, the `$0.01` hosted-search call rate, and `OPENAI_USD_TO_EUR` (default `1`) for the euro envelope. Unreviewed model IDs fail before a live request. Stage usage records the pricing version, conversion rate, cached input, and active tool cap.
- Programme-only funding calls or schemes without an identified commissioning buyer/concrete applicant persist as source-level Signals. Only organization-specific candidates enter Organization/Opportunity resolution and qualification.
- Source Monitor discovery is intentionally recall-oriented before qualification: concrete current project signals survive when budget, contact, route, or addressable scope is unknown, then assessment/research decides whether they qualify. Empty monitor output is valid only with a persisted zero-result reason.
- `20260926160000_atomic_signal_revision_persistence.sql` separates canonical page provenance from candidate-specific logical source-item identity. The service-only persistence RPC serializes writes per source, reuses canonical URL/fingerprint matches on retry, and atomically assigns revisions; durable resolve snapshots created before this change derive the same `web-v1` identity when retried.
- Live stages emit structured, credential-redacted `[automation]` start/completion/failure events to the Next.js server terminal and retain durable failure details in stage history. Provider-incomplete failures have their own operational code. Handled dashboard fallbacks log as warnings and preserve the failed query plus sanitized PostgREST code, message, details, and hint instead of collapsing structured errors to `[object Object]` or opening a Next.js error overlay.
- Source Network reconstructs each monitor's search, candidate, validation, and resolution counts from durable stage snapshots. Existing and new successful zero-result runs are visibly explained; the Lead gallery points empty authenticated workspaces to this operational history. Strategy/source actions, queue-empty states, Source Network snapshots, and dashboard load failures also emit sanitized server logs.
- Live agent stages default to a configurable 150-second foreground deadline (`AUTOMATION_AGENT_TIMEOUT_SECONDS`, bounded to 30–240 seconds), receive a database lease 30 seconds longer than that deadline, and run behind automation routes with a 300-second deployment ceiling.
- Search-agent Responses allow 4,000 provider output tokens because that ceiling includes hidden reasoning tokens; focused discovery/research prompts target approximately 1,200 concise output tokens while Source Scout targets approximately 2,200 for up to five evidence-bearing proposals, and the workflow cost envelope remains enforced.
- Exact Organization/Opportunity resolution, immutable Signals, automated Assessments with null `assessed_by`, Research Questions/Findings, automatic review-ready Leads, and explicit qualification exceptions.
- Active policy `2026-09-25.2`: weights total 100%; Budget and Delivery require 6/10 at 0.65 confidence, and either Social impact or Technical fit must meet the same 6/10 and 0.65 gate. It adds potential-aware initial research and terminal Monitoring for still-unavailable public facts; historical `2026-09-25.1` Assessments remain immutable. €30k minimum, €50k–€100k preferred, and €250k review defaults are editable. Assessments distinguish whole-procurement, explicit-lot, dedicated-package, proxy, and unknown commercial scope.

- Final routing is ordered and deterministic. Only `score.decision = qualify` plus every persisted gate may create a Lead. Proven poor fit rejects; promising cases with still-unavailable public commercial/contact/capability/timing evidence become `monitoring`; conflicts, sensitive sectors, unusual scope, partner dependency, internal capacity ambiguity, borderline scores, or invalid outreach enter Needs attention.
- Technical capability fit is citation-backed project evidence with matched YipYip services and unsupported/unresolved requirements. Delivery capacity is the operator-owned effective-dated staffing input. They persist separately in Assessment qualification checks and route to distinct `capability_fit_uncertain` and `delivery_capacity_uncertain` exceptions; the Evaluation drawer shows both rather than implying that “available” capacity proves project capability.

- The drawer separates **Resolve** for non-Lead qualification exceptions from **Decision** for finished Leads. Resolve atomically queues focused reassessment or records an Opportunity pass while updating the exception/lifecycle/history; Decision supports Start pursuing, Pass on Lead, Research a gap, and route changes against an exact Lead version. The session basket opens the `/reviewed` Pursuit workspace, which additionally groups quarantined historical Leads under Needs requalification. Demo state remains in `sessionStorage` and includes simulated drafts and resolutions.
- The dashboard independently projects every queued/running `opportunity_qualification` workflow as active research, including normal `signal_created` workflows as well as explicit review requests. Citation-backed named-person, responsible-team, procurement-desk, or tender-channel findings are projected into the Lead; an otherwise promising case with two unknown attempts becomes Monitoring rather than a false rejection or qualified Lead.

## Active decisions

- One active Lead Strategy per workspace initially, with immutable version history.
- Interface translation covers product chrome and workflow controls; external source text, evidence excerpts, organization names, and persisted operator/provider errors are not machine-translated.
- Source approval is the only routine human gate before monitoring. Agents never approve sources.
- Approved sources run every weekday at 07:00 in the strategy timezone; Source Scout reruns on material strategy changes and every 30 days.
- One protected invocation performs one bounded stage so workflows remain resumable and request-duration safe.
- Provider-output contract mismatches receive one automatic retry; a second mismatch stops with its specific operational code rather than repeating the same request four times.
- Exact deterministic entity matching is automatic. Ambiguous/probabilistic matches go to Needs attention.
- Qualified Opportunities automatically create review-ready Leads only when the final Assessment decision is `qualify` and every persisted check passed. Rejected, quarantined, and in-progress Opportunities stay out of the default gallery.
- Manual pursuit is a separate attributed human override, never an alternate path through the automatic qualification guard. It may expose a completed Opportunity in the pursuit pipeline, but must keep the automated state visible and may not override hard-sector or expired-actionability rejection.
- A provisional low weighted score does not suppress research when at least one YipYip fit axis is promising and material evidence is unresolved. Bounded unavailable public facts route to Monitoring; agents cannot turn uncertainty into qualification.
- Automatic qualification requires a supported actionable contact route; inferred labels trigger bounded research and terminal unavailable public evidence routes to Monitoring. Conflicting routes remain Needs attention.
- Internal Search Plan snapshots retain query reproducibility; users never manage Query Packs.
- Live automation and Cron default off. Draft generation is authorized inside qualification, but no deployment, outreach sending, CRM mutation, or delivery action occurs without explicit authorization.

## Known limitations

- A fresh local workspace with three approved sources was observed to complete six source-monitor cycles with hosted search but zero generated candidates. RLS was verified independently: the owner can read all seven workflows and nineteen stages. The discovery prompt was too conservative because it asked for plausible budget fit before assessment; it now retains concrete current project signals with unknown qualification facts. The adjusted prompt has mocked coverage but has not been exercised through a new billable monitor run.
- The corrected policy and schema pass a clean local non-billable gate, but the original live validation hypothesis still requires a new controlled campaign. The three governed local sources were recovered after the required reset. The active restored Strategy has `capacity_status = unknown`, so no vendor run was started: unknown capacity must enter Needs attention and cannot legitimately produce an auto-qualified Lead.
- Hosted Cron/Vault remains unconfigured. Earlier bounded Source Scout attempts against a custom Responses endpoint did not report or execute a hosted web-search call in a form the SDK could verify; those runs were correctly rejected and nothing was persisted. Later official-endpoint runs performed hosted search but omitted the optional raw search-source list, so deterministic citation validation rejected every proposal; source-list inclusion is now corrected, but a successful post-fix end-to-end live run is still pending.
- Agent cost is an estimate; the first controlled source-monitor smoke cost €0.076098 and returned one candidate, but the candidate was correctly rejected for an out-of-lookback publication and a source URL that did not exactly match the provider-cited PDF/HTML variant. A labeled evaluation set and more controlled source runs are still required to calibrate quality, thresholds, URL equivalence, and cost.
- The Agents SDK currently reduces an unsuccessful `response.incomplete` event to a generic model-behavior error, so the exact provider `incomplete_details.reason` is not available through the existing non-streaming runner path. The official reasons are max output tokens, max messages, content filtering, or steering.
- The first live approved-source monitor repeatedly reached the former 60-second foreground deadline. The coordinated limit is now 150 seconds by default; genuinely longer multi-search work still requires a durable Responses background-mode integration rather than an unbounded HTTP request.
- Source Monitor currently uses the hosted web-search path scoped to an approved source; source-specific feed/API adapters remain future work.
- Entity resolution is exact only. Persistent pursuit/pass/research/route review and outreach drafting are implemented; field correction, merge/split review UI, delivery/export, CRM, outreach sending, and proposal generation remain future.
- The public demo is deterministic `sessionStorage`, not live research or an authenticated demo account.
- Basket contents remain client-session only; the shared header basket is available across the three primary application pages, and `/reviewed` combines that shortlist with persistent Lead/review state but does not make the shortlist itself durable.
- The resilient Source Scout boundary is covered by mocked contract tests but has not yet been exercised by another billable live Source Scout call. The already queued historical retry can exercise the fixed code after the development server reloads.
- Two local resolve stages failed under the former page-URL-as-item-ID behavior after their source pages each produced three accepted candidates. Their attempt-2 resolve stages remain queued and can resume through the new compatibility path after the development server reloads; this repair was verified without advancing those live workflows or making a provider call.
- Qualification cost enforcement still evaluates a stage after its provider response, so a response can exceed the remaining envelope before continuation stops. Model-aware estimates and the three-call Research cap materially reduce this exposure, but a conservative preflight reservation remains future work. Historical workflow costs retain the estimator used when they ran and are not recalculated.
